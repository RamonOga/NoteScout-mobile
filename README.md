# NoteScout — мобильный клиент

Flutter-приложение для заметок и ссылок: вход и регистрация, работа с сессией,
дальше — список заметок, теги и поиск.

Бэкенд: [NoteScout-backend](https://github.com/RamonOga/NoteScout-backend)

---

## Состояние

Готово:

* структура проекта и слой доступа к API;
* хранение сессии в Keychain (iOS) и Keystore (Android);
* автоматическое обновление access-токена при 401;
* экраны входа и регистрации с валидацией и понятными ошибками;
* маршрутизация с правилами доступа: без сессии — только вход и регистрация;
* **список записей**: поиск по тексту, фильтр по тегам (режимы «любой»/«все»),
  фильтр по типу, показ архива, подгрузка страниц, pull-to-refresh;
* **редактор**: заметка или ссылка, теги, архивирование, удаление
  с подтверждением;
* **корзина**: режим «Удалённые» и восстановление записи;
* **оффлайн**: без связи показываются последние загруженные данные, с честной
  полосой «нет связи» — выдавать старое за свежее нельзя;
* **вложения**: файлы к заметке — загрузка с прогрессом, список, удаление и
  просмотр картинок;
* 88 тестов: интерсептор, разбор ошибок, хранилище сессии, формы, сборка
  параметров запроса, пагинация, состояния списка, корзина, оффлайн-кеш,
  вложения;
* **иконка приложения** и **релизный APK**: сборка локально или в CI по тегу
  (`.github/workflows/release-android.yml`).

Дальше: правка записей оффлайн (сейчас запись только онлайн), просмотр
вложений кроме картинок (нужен плагин для открытия файлов) и сборка релизного
IPA — для неё нужен macOS.

## Веб-предпросмотр

Приложение собирается и под web — это самый быстрый способ посмотреть
интерфейс без эмулятора:

```bash
flutter run -d chrome --dart-define=API_BASE_URL=http://localhost:8080/api/v1
```

Если `API_BASE_URL` не задавать, на веб-сборке адрес выводится из адреса самой
страницы. Это удобно, когда статика и API отдаются с одного источника: запросы
уходят туда же, откуда открыта страница, и CORS не участвует. На телефоне
поведение прежнее — `10.0.2.2`.

## Запуск

Базовый URL API задаётся при сборке через `--dart-define`:

```bash
# Android-эмулятор: 10.0.2.2 — это хост-машина с его точки зрения
flutter run

# iOS-симулятор
flutter run --dart-define=API_BASE_URL=http://localhost:8080/api/v1

# Реальный сервер
flutter run --dart-define=API_BASE_URL=https://notes.example.com/api/v1
```

Значение по умолчанию — `http://10.0.2.2:8080/api/v1`, то есть локальный
бэкенд из `docker-compose.dev.yml`, поднятый на этой же машине.

Телефон на том же Wi-Fi, что и компьютер, потребует адреса вида
`http://192.168.x.x:8080/api/v1` — и бэкенд должен слушать не только localhost.

## Структура

```
lib/
├─ main.dart                      точка входа: читает сессию и запускает приложение
├─ app.dart                       MaterialApp с маршрутизацией
├─ core/
│  ├─ config/app_config.dart      адрес API и таймауты
│  ├─ error/api_exception.dart    единый формат ошибки бэкенда
│  ├─ models/user.dart            пользователь
│  ├─ network/auth_interceptor.dart  подстановка и обновление токена
│  ├─ providers.dart              сборка зависимостей (Riverpod)
│  ├─ router/                     маршруты и правила доступа
│  ├─ session/                    сессия и её защищённое хранение
│  └─ theme/app_theme.dart        оформление
└─ features/
   ├─ auth/
   │  ├─ data/auth_api.dart       вызовы /auth/* и /users/me
   │  ├─ application/auth_service.dart  сценарии входа, регистрации, выхода
   │  └─ presentation/            экраны входа и регистрации
   └─ notes/presentation/         пока заглушка после входа
```

Разделение по слоям простое: `data` знает про HTTP, `application` — про сценарии,
`presentation` — про виджеты. Слой с состоянием появится вместе с заметками.

## Решения, которые стоит знать

**Сессия — единственный источник правды.** `SessionStore` наследуется от
`ChangeNotifier` и одновременно служит `refreshListenable` для go_router.
Как только сессия появилась или пропала, маршрут пересчитывается сам. Отдельного
флага «пользователь вошёл» в приложении нет — иначе он рано или поздно разъедется
с хранилищем.

**Обновление токена живёт в интерсепторе.** Любой запрос, получивший 401,
прозрачно повторяется с новым токеном. Ротация выполняется ровно один раз, даже
если 401 пришёл сразу от нескольких параллельных запросов: остальные ждут тот же
`Future`. Без этого несколько одновременных ротаций отозвали бы друг друга —
на бэкенде повторное использование refresh-токена считается кражей.

**Запросы к `/auth/*` не повторяются.** Их 401 означает неверные учётные данные,
а не истёкший access-токен.

**Токены хранятся только в защищённом хранилище.** SharedPreferences для этого
не годятся: их читает любое приложение с root, и они попадают в резервные копии.

## Сборка

### Локально

```bash
# APK для установки на телефон
flutter build apk --release \
  --dart-define=API_BASE_URL=https://notescout.duckdns.org/api/v1

# iOS (только на macOS)
flutter build ipa --release \
  --dart-define=API_BASE_URL=https://notescout.duckdns.org/api/v1
```

Готовый файл — `build/app/outputs/flutter-apk/app-release.apk`. Это «толстый»
APK: в нём сразу все архитектуры. Если размер важен, `--split-per-abi` соберёт
отдельные файлы под arm64-v8a и armeabi-v7a — они меньше, но ставить придётся
тот, что подходит телефону.

### Подпись

Если ничего не настраивать, релизная сборка подписывается отладочным ключом.
Такой APK ставится на телефон и работает, но:

* отладочный ключ генерируется заново на каждой машине (и на каждом запуске
  CI), поэтому обновить установленное приложение сборкой с другим ключом
  нельзя — Android потребует сначала удалить приложение;
* его нельзя загрузить в Google Play.

Свой ключ заводится один раз:

```bash
keytool -genkey -v -keystore android/app/release.jks \
  -keyalg RSA -keysize 2048 -validity 10000 -alias notescout
```

Затем рядом создаётся `android/key.properties`:

```properties
storeFile=release.jks
storePassword=<пароль хранилища>
keyAlias=notescout
keyPassword=<пароль ключа>
```

`storeFile` указывается относительно `android/app/`. Пароль берите из букв и
цифр: `key.properties` — это Java properties, и символы `\`, `=`, `:` в пароле
пришлось бы экранировать.

Оба файла перечислены в `.gitignore`. `android/app/release.jks` — **единственная
копия ключа**: потеряв его, выпустить обновление для уже установленного
приложения будет невозможно. Ключ стоит положить в бэкап.

### В CI

`.github/workflows/release-android.yml` собирает APK на стороне GitHub — это
удобно, когда не хочется ставить Android SDK локально или нужно отдать файл
кому-то ещё. Запуск:

* вручную — Actions → Release APK → Run workflow (адрес API можно
  переопределить, по умолчанию берётся продовый);
* тегом — `git tag v1.0.0 && git push origin v1.0.0`; тогда APK дополнительно
  прикладывается к GitHub Release.

В обоих случаях APK лежит в артефактах запуска (`Artifacts` внизу страницы
сборки).

Чтобы CI подписывал релизным ключом, добавьте в Settings → Secrets and
variables → Actions четыре секрета:

| Секрет | Значение |
|---|---|
| `ANDROID_KEYSTORE_BASE64` | `base64 -w0 android/app/release.jks` |
| `ANDROID_KEYSTORE_PASSWORD` | пароль хранилища |
| `ANDROID_KEY_ALIAS` | `notescout` |
| `ANDROID_KEY_PASSWORD` | пароль ключа |

Без этих секретов workflow не падает: он соберёт APK, подпишет его отладочным
ключом и напишет об этом в описании релиза. Если задан только
`ANDROID_KEYSTORE_BASE64`, сборка останавливается с ошибкой — частично
заполненные секреты означают ошибку в настройке, а не повод молча выпустить
сборку не тем ключом.
